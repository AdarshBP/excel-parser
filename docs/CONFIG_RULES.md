# How to build the excel parser configuration workbook (rules)

The configuration workbook is the only place where sheet and column knowledge
lives. `validator.py` checks it and turns it into DDL, `executor.py` uses the
same workbook to read the source file and push the rows. No sheet name, row
number or column letter is ever hardcoded in the code.

**Start from `template/config_template.xlsx`.** It is a working configuration
with the three sheets, the exact headers, a hover comment on every header, one
example block to copy, and `help_*` sheets repeating each header with its
allowed values. Copy it, rename it after your source file, replace the example
rows. The three example configurations carry the same notes and `help_*` sheets;
`python3 tools/make_template.py <config>.xlsx --annotate` adds them to any other
configuration workbook.

Every rule below is enforced by `validator.py`, so run it against your
configuration (and a real source file) before pushing anything:

```bash
python3 tools/validator.py my_config.xlsx my_source.xlsx
```

The workbook has three sheets, named **`target_config`** (where the data goes),
**`sheet_config`** (which blocks to read) and **`column_config`** (which cells).
The sheet names, and the column headers on row 1 of each, must match exactly -
they are read by name. `target_config` may be left out, in which case the
defaults below apply.

---

## 0. `target_config` - where the data is pushed

Two columns are read, `setting` and `value` (a third column such as `notes` is
ignored), one setting per row:

| setting | Default | Meaning | Rules |
|---|---|---|---|
| `target` | `sqlite` | which database engine | `sqlite` or `postgres`. |
| `database` | - | SQLite: the file path (`sales.db`). PostgreSQL: the database **name** (`excel_parser`). | For PostgreSQL it must be a plain name - letters, digits, underscores. |
| `db_schema` | `public` | PostgreSQL schema to load into, created if absent | plain name; ignored by SQLite, which has no schemas. |
| `table_prefix` | *(blank)* | put in front of every generated table name | plain name fragment; blank means the table is just `table_name`, `` would give `sales`. |
| `id_type` | `integer` | how primary keys and `file_id` are generated | `integer` = a database counter (1, 2, 3...); `uuid` = a UUID generated per row. |

```
setting        value       notes
target         postgres    sqlite | postgres
database       excel_parser    sqlite: file path. postgres: database name
db_schema      staging     created if absent; blank = public
table_prefix               blank = none;  would give sales
id_type        integer     integer | uuid
```

Rules that matter:

1. **Never put credentials here.** Host, port, user and password are read from
   the environment / `.env` only (`PGHOST`, `PGUSER`, `PGPASSWORD`, ...). A
   workbook is mailed around and committed; a password in it is a leak. The
   validator rejects credential-looking settings.
2. **The command line wins.** `--target`, `--database` and `--prefix` on
   `validator.py` / `executor.py` override the workbook, so the same
   configuration can be pointed at dev and at production without editing it.
3. **`database` may be left blank**, and then it has to come from the command
   line (SQLite) or `PGDATABASE` (PostgreSQL).
4. Changing `table_prefix` or `db_schema` means a different set of tables -
   regenerate the DDL before loading.
5. `id_type` decides the key columns for every table in the workbook - you
   cannot mix the two. `integer` gives `BIGINT ... IDENTITY` / `INTEGER
   PRIMARY KEY AUTOINCREMENT`; `uuid` gives `UUID` on PostgreSQL and `TEXT` on
   SQLite, with the value generated by the loader (no database extension
   needed). Existing tables were created for one of the two, so changing it
   means new tables: regenerate the DDL and load into a fresh prefix/schema.

## 1. `sheet_config` - one row = one table

| Column | Required | Meaning | Rules |
|---|---|---|---|
| `table_name` | yes | logical table name | lowercase `snake_case`, letters/digits/underscore only, must be unique in the workbook. The physical table becomes `<prefix><table_name>`, and the prefix is blank by default. |
| `sheet_name` | yes | worksheet in the source file | must match the tab name **character for character** (Excel truncates long tab names, e.g. `Growth Investments and Other De`). If no sheet matches, the block is skipped silently. |
| `layout` | yes | `table` or `key_value` | `table` = a header row with data rows underneath. `key_value` = a label column and a value column (a header block). It is documentation for the reader; both are read the same way, cell by cell. |
| `header_row` | no | row holding the headers | recorded in the audit table and used for readability only; the loader does not read data from it. Leave blank for `key_value`. |
| `data_start_row` | yes | first row of real data | 1-based, as shown in Excel. Must be **below** any title/header row. |
| `data_end_row` | no | last row of real data | leave blank to read to the end of the sheet. Set it to exclude totals rows, notes, or a second block further down. |
| `active` | yes | `Y` / `N` | `N` = no table generated and nothing loaded. Use it to park a block instead of deleting the rows. |
| `description` | no | what the table represents | written as a `COMMENT ON TABLE` in PostgreSQL so AI agents and BI tools can discover meaning. |
| `domain` | no | business domain / category | e.g. `finance`, `sales`, `food_delivery`. Prepended to the table comment as `[domain]`. |
| `notes` | no | free text | copied into the generated SQL as a comment. |

Rules that matter:

1. **One block = one row here.** If a worksheet contains two header blocks
   (e.g. "Card" on row 3 and "Cash" on row 9), add **two** rows with the same
   `sheet_name` and different `table_name` / row ranges. Do not try to merge
   them.
2. **Ranges are read literally.** Everything between `data_start_row` and
   `data_end_row` is read. Rows are only dropped when they are completely empty
   or when a `nullable = N` column is empty (those are reported on screen).
3. **Never point two active rows at the same `table_name`.**
4. Adding, removing or renumbering rows requires regenerating the schema
   (step 2 in `RUNNING.md`) before the next load.

## 2. `column_config` - one row = one database column

| Column | Required | Meaning | Rules |
|---|---|---|---|
| `table_name` | yes | must match a `sheet_config.table_name` | rows whose table is missing or inactive are ignored. |
| `source_ref` | yes | which Excel column to read | format `col:<letter>`, e.g. `col:A`, `col:AM`. Uppercase letters, no row number, no ranges, no formulas. |
| `source_header` | no | header text as printed in the file | Documentation only - so a human can see which header a column came from. **Not used for matching or logic.** The parser reads by `source_ref` (column position), never by header text. If empty, the column still loads fine - you just lose the human-readable label in the ER diagram and preview tooltips. A renamed header in the source file does not break the load. |
| `column_name` | yes | database column name | lowercase `snake_case`, unique **within the table**, must not be `file_id`, `sheet_name`, `source_row_num` or `<table_name>_id` (the loader adds those). |
| `data_type` | yes | one of `text`, `numeric`, `integer`, `date`, `timestamp`, `boolean` | anything else stops schema generation with an error. |
| `nullable` | yes | `Y` / `N` | `N` = `NOT NULL` in the schema, and any source row with that cell empty is rejected and reported instead of failing the load. Keep it `Y` unless the cell is genuinely always filled. |
| `is_key` | yes | `Y` / `N` | `Y` only creates a non-unique index (e.g. on `order_id`). It is **not** a primary key and does not deduplicate. |
| `transform` | no | `trim`, `money`, `percent`, `date`, blank | documentation of intent; the actual cleaning is driven by `data_type` (see below). |
| `column_order` | yes | integer | controls the column order in the generated table. Gaps are fine; duplicates make the order arbitrary. |
| `references` | no | `table_name.column_name` | declares a foreign-key relationship to another table's column, drawn as a dashed line in the ER diagram. Does not create a database constraint - it is for documentation and the diagram only. |
| `null_default` | no | the value to use when a cell is empty | blank or `null` = store NULL (the default). For `numeric`/`integer` columns, `0` stores zero instead of NULL. For `text`, any string (e.g. an empty string or `N/A`). For `boolean`, `0`/`1`/`true`/`false`. Applied after type casting, so a cell with `-` that casts to NULL will also get the default. |
| `script` | no | predefined transformation | applied after type casting on every cell. Chain with `\|`: `trim\|uppercase`. Errors block the push. See script list below. |
| `description` | no | what this column means | written as a `COMMENT ON COLUMN` in PostgreSQL. AI agents and BI tools read these to understand the schema without documentation. |
| `unit` | no | unit of measurement | e.g. `INR`, `USD`, `percent`, `kg`, `count`. Appended to the column comment in parentheses. |

### Available scripts

| Script | Applies to | What it does |
|---|---|---|
| `uppercase` | text | Convert to UPPER CASE |
| `lowercase` | text | Convert to lower case |
| `titlecase` | text | Capitalize Each Word |
| `trim` | text | Strip leading/trailing whitespace |
| `strip_spaces` | text | Remove all whitespace |
| `digits_only` | text | Keep only digits |
| `letters_only` | text | Keep only letters |
| `alphanum_only` | text | Keep only letters and digits |
| `abs` | numeric/integer | Absolute value |
| `round_2` | numeric | Round to 2 decimal places |
| `round_0` | numeric | Round to 0 decimal places |
| `floor` | numeric/integer | Round down |
| `ceil` | numeric/integer | Round up |
| `negate` | numeric/integer | Flip the sign |
| `date_only` | timestamp | Strip time, keep YYYY-MM-DD |
| `year_month` | date/timestamp | Extract YYYY-MM |
| `not_null` | any | Error if the value is NULL |

Chain with `|`: `trim|uppercase` runs trim first, then uppercase.
Scripts skip NULL values automatically (except `not_null`).

Rules that matter:

1. **Only configured columns are loaded.** An Excel column with no row here is
   ignored - that is the way to leave junk columns out.
2. **Two Excel columns with the same header need two different
   `column_name`s** (e.g. two "Delivered Orders" columns become
   `swiggy_delivered` and `toing_delivered`). Duplicates otherwise fail with
   `duplicate column name`.
3. **Choose the type from the worst value in the column, not the first.** If any
   cell can hold `-`, `NA` or a note, use `text`. A value that does not fit its
   type is stored as `NULL` and listed at the end of the load, e.g.
   `order_level: Order Level!AV78 -> cancellation_time stored as NULL,
   '75.4' is not a date` - treat that as a prompt to correct `data_type`.
4. `col:` letters must be re-checked whenever the supplier inserts a column in
   the source file - the loader reads by position, not by header.
5. `table_name` and `column_name` must be plain names: letters, digits and
   underscores, starting with a letter or underscore, 63 characters at most.
   Anything else is refused up front (these names are the only part of the
   configuration that becomes SQL text; every cell value is bound as a
   parameter).

## 3. What the types do to the value

| `data_type` | Conversion applied by the loader | Example |
|---|---|---|
| `text` | trimmed; empty string becomes `NULL` | `" VISA "` -> `VISA` |
| `numeric` | strips everything except digits, `.` and `-`; a leading `(` becomes `-` | `₹1,234.50` -> `1234.5`, `18%` -> `18.0`, `(₹120.00)` -> `-120.0` |
| `integer` | as `numeric`, then truncated to a whole number | `"42.0"` -> `42` |
| `date` | real Excel dates -> `YYYY-MM-DD`; common text formats parsed; `-`/`NA` -> `NULL`; anything else stored as `NULL` and reported | `2026-08-02 00:00` -> `2026-08-02` |
| `timestamp` | as `date`, keeping the time | order placed-at columns |
| `boolean` | `y/yes/true/1` -> 1, `n/no/false/0` -> 0, anything else `NULL` | `Yes` -> `1` |

Note `18%` becomes `18.0`, not `0.18`. Staging keeps the printed value; convert
in your reporting layer if you want a fraction.

## 4. Columns every generated table gets for free

```sql
<table_name>_id   -- surrogate key
file_id           -- which physical file/load, FK to source_file
sheet_name        -- worksheet the row came from
source_row_num    -- 1-based Excel row number
```

plus `UNIQUE (file_id, sheet_name, source_row_num)`, so a row can always be
traced back to one exact cell block, and the same worksheet row cannot be
loaded twice under one `file_id`.

Two control tables are always generated:

* `source_file` - file name, SHA-256, `source_ref` (the original reference:
  Drive file ID, Sheets link, or local path), row count, load timestamp.
  The hash is unique, so re-loading a byte-identical file is refused.
  An AI agent can read `source_ref` to trace back to the original file.
* `load_config_audit` - for each table: the sheet, the row range/column
  count, and `config_ref` (the configuration workbook reference) that
  were actually used for that load.

---

## 5. What must never go into the configuration workbook

Database host names, users, passwords or connection strings. The PostgreSQL
target reads those from the environment / a `.env` file only (see
`RUNNING.md`), so the configuration workbook can be shared and version
controlled freely.

---

## 6. Checklist before you hand a configuration over

- [ ] Sheet tab names copied exactly from the source workbook.
- [ ] `data_start_row` is the first data row, not the header.
- [ ] `data_end_row` set wherever a totals row or a second block follows.
- [ ] Every block on a shared sheet has its own `table_name`.
- [ ] `column_name` unique per table, `snake_case`, not a reserved lineage name.
- [ ] `data_type` chosen from the messiest value in the column.
- [ ] `nullable = N` only on cells that are always populated.
- [ ] `column_order` filled in.
- [ ] Schema regenerated after any change, and the load re-run on a fresh file.
